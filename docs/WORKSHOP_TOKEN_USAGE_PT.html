02 · Fundamentos

LLMs não lembram — você lembra

A cada turno, seu cliente reenvia todo o histórico da conversa. O modelo em si é stateless. Clique em Próximo turno para ver uma requisição real crescendo.

A conversa é uma ilusão

Claude Code mantém o histórico na sua máquina. A cada turno, ele monta tudo junto e envia uma nova chamada de API. O modelo vê o transcript inteiro do zero cada vez — ele não tem memória entre chamadas.

IDEIA CENTRAL

Toda regra mais adiante neste workshop deriva desse único fato: se o cliente precisa reenviar tudo a cada turno, históricos mais curtos custam menos. É exatamente isso que caching, skills, scripts e higiene fazem.

04 · Contexto

Context windows são memória de trabalho

Tudo que o modelo "lembra" vive na janela. Quando ela enche, as coisas quebram.

200k tokens

Janela padrão. ~500 páginas de texto. Suficiente para a maioria das tarefas.

1M tokens

Disponível no Opus 4.6. Para bases de código muito grandes ou análises longas — mas caro e mais lento.

04 · Degradação de contexto

Mais contexto ≠ melhores respostas

A partir de certo ponto, encher a janela não ajuda o modelo — prejudica. Instruções se perdem, restrições são ignoradas, respostas se degradam.

Encontrando uma instrução de tamanho fixo
janela de 200k →

A agulha rosa tem sempre os mesmos ~200 tokens em cada linha. O que muda é o palheiro ao redor.

limite de 200k
20k · início da sessão ~98% de recall
80k · meio da sessão ~90% de recall
150k · sessão longa ~72% de recall
190k · próximo do limite ~55% de recall
AGULHA EM 20k
1 parte em 100
AGULHA EM 190k
1 parte em 950

A instrução é a mesma — mas ao final de uma sessão longa, ela é ~10× mais difícil de encontrar no meio de tudo o que o modelo precisa atender.

sua instrução · ~200 tokens · fixo
histórico ao redor · crescendo

Como a degradação aparece na prática

  • Esquece uma restrição que você definiu 15 turnos atrás
  • Pede novamente um caminho de arquivo que você já deu
  • Contradiz decisões anteriores silenciosamente
  • Perde detalhes no meio de um arquivo longo
  • Segue a instrução mais recente mesmo que conflite com regras estabelecidas

Por que acontece

Atenção é finita. Com mais tokens para atender, cada um recebe uma fatia menor. Modelos também têm viés posicional — eles lembram o início e o fim do contexto muito melhor do que o meio.

REGRA PRÁTICA

Não julgue a qualidade da resposta do Claude pelo turno 2 de uma sessão longa. No turno 40, é um modelo diferente (pior) respondendo. Quando as respostas começarem a se degradar, inicie uma nova sessão — quase sempre é mais rápido do que lutar com uma sessão inchada.

05 · Caching

Prompt caching — a maior alavanca

Claude faz cache da parte estática do seu prompt. Se o próximo turno corresponder, você paga ~10% do custo de input.

A regra de 1 hora

Entradas de cache vivem até 1 hora. Cada turno dentro dessa janela renova o cache. Fique ocioso além disso → cache miss → custo cheio novamente.

O que Claude Code faz cache para você

  • System prompt
  • Arquivos CLAUDE.md
  • Definições de ferramentas
  • Turnos anteriores da conversa

Modelo mental

Pense no cache como um motor quente. Continue enviando turnos → motor fica quente → barato. Fique parado por uma hora → motor esfria → o próximo turno paga o preço cheio para religar.

05 · Anatomia de um prompt

O que está no prompt — e o que fica em cache

Cada turno envia a pilha inteira. Caching significa que você paga o preço cheio apenas pela parte nova no final.

A matemática

Tamanho total do prompt~59.080 tok
Porção em cache59.000 tok
Porção nova80 tok
Você paga como se enviasse~6.000 tok

Por que funciona

Claude faz hash do prefixo do seu prompt. Se o prefixo do próximo turno corresponder a um em cache, Claude reutiliza o estado computado em vez de reprocessar do zero.

O cache é reutilizado se você enviar outro turno dentro de 1 hora.

IDEIA CENTRAL

O prefixo precisa corresponder exatamente. Altere o CLAUDE.md, adicione uma ferramenta ou edite um turno anterior → todo o cache a partir desse ponto é invalidado.

Como sua assinatura realmente mede seu uso

Todos vocês estão no Pro ou Max. O custo não é em dólares — são dois limites sobrepostos e uma válvula de segurança.

Limite 1

Janela rolante de 5 horas

Cada mensagem que você envia inicia (ou renova) uma janela de 5 horas. Dentro dessa janela você tem um balde de uso — atinja o limite e você fica pausado até a janela expirar.

reinicia continuamente · não na hora em ponto

Limite 2

Teto de uso semanal

Além das janelas de 5 horas, há um teto rolante de 7 dias. É o orçamento real — o limite de 5 horas apenas impede que você queime a semana em uma tarde.

maior no Max · muito maior no Max 20x

Válvula de segurança

Créditos extras

Atingiu um limite? Você pode recarregar com créditos pay-as-you-go para continuar. Mas estes são cobrados às tarifas de API — visivelmente mais caros por token do que o que sua assinatura oferece. Uma rede de segurança, não um plano.

ativar no console · definir um limite de gasto

DICA · DISTRIBUA A CARGA Use suas janelas — não as queime

Sessões pesadas seguidas durante a manhã toda → você atinge o limite de 5 horas no almoço e fica parado o resto do dia. Distribua o trabalho ao longo do dia para que cada janela de 5 horas produza resultado real. Uma sessão rápida depois do almoço mantém a janela ativa sem bloquear você mais tarde.

POR QUE HIGIENE IMPORTA

Cada regra neste workshop — caching, skills, scripts, subagents — estende diretamente sua janela de 5 horas e sua semana. Boa higiene = mais trabalho antes do limite, e menos recargas forçadas às tarifas de API.

07 · Escolha de modelo

Escolha o modelo certo para o trabalho

Mesma tarefa, três modelos → custo, velocidade e qualidade completamente diferentes. Hábitos padrão deixam dinheiro real na mesa.

Rápido & barato

Haiku 4.5

Custo1×
Velocidademais rápido
Teto de qualidadebom

Use para: edições simples, classificação, boilerplate, explicações curtas, pré-filtragem antes de um modelo maior.

Padrão equilibrado

Sonnet 4.6

Custo~3×
Velocidaderápido
Teto de qualidadeforte

Use para: a maioria dos trabalhos com Claude Code — refatorações, debugging, mudanças em múltiplos arquivos, revisões, escrita. O padrão certo para 80% das sessões.

Raciocínio pesado

Opus 4.6

Custo~15×
Velocidademais lento
Teto de qualidademais alto

Use para: decisões difíceis de arquitetura, bugs complicados, análises longas, qualquer coisa onde uma resposta errada custa mais do que o modelo.

Esforço ajustável (extended thinking)

Mesmo modelo, diferentes orçamentos de raciocínio. Pouco esforço = resposta rápida. Muito esforço = o modelo gasta mais tokens raciocinando internamente antes de responder — melhor em problemas complexos, mas mais lento e mais caro.

Trate como um segundo dial ao lado da escolha de modelo: Sonnet + alto esforço muitas vezes supera Opus + padrão a uma fração do custo.

REGRA PRÁTICA

Inicie sessões com Sonnet. Desça para Haiku em trabalhos repetitivos. Escale para Opus (ou aumente o esforço) apenas quando a qualidade justifica pagar 5–15× mais. Troque modelos dentro do Claude Code com /model.

08 · Planeje primeiro

Para tarefas complexas, planeje antes de executar

Uma virada errada em uma tarefa longa queima tokens, limite e tempo. Faça o agente explicar sua intenção antes de começar a escrever código.

O fluxo de planejamento antecipado
1

Peça um plano — não execução

"Não altere nada ainda. Explique o que você faria, quais arquivos você tocaria e por quê." Use o modo de planejamento (shift+tab) para fixar isso.

2

Revise & corrija o plano

Questione. Corrija suposições erradas. Ajuste o escopo. Itere até o plano estar aprovado por você — este é o momento mais barato para corrigir o rumo.

3

Salve o plano como documento

"Escreva este plano em PLAN.md." Um artefato durável — sobrevive à sessão, revisável por um colega, reutilizável se você tentar novamente.

4

Nova sessão → execute a partir do plano

Contexto limpo. Carregue apenas o PLAN.md. O modelo começa com a cabeça limpa e um briefing focado — sem arrastar toda a sessão de brainstorm.

Por que isso vale a pena

Viradas erradas em tarefas longas se compõem. Quando você percebe, 40k tokens de direção errada estão no contexto — e corrigi-los significa mais turnos, mais tokens e um agente mais confuso. Uma revisão de plano de 5 minutos previne uma hora de limpeza.

Anti-padrão

"Só faz" em uma tarefa complexa

Você digita uma linha. O agente roda por 20 minutos, edita 14 arquivos, e então você percebe que ele entendeu errado o requisito. Agora a sessão está inchada, o diff é uma bagunça, e você está pagando para desfazer tudo.

REGRA GERAL

Se a tarefa toca > 3 arquivos ou leva > 10 minutos para executar, planeje primeiro. A própria sessão de planejamento é barata — o modo de planejamento não faz chamadas de ferramentas, não faz edições, não desperdiça nada.

13 · Aprendizados

Quatro regras para levar daqui

Se você não lembrar de mais nada, lembre-se destas.

REGRA 01

Se os dados brutos > sua resposta, escreva um script primeiro

O LLM não deveria processar o que Python pode. Pague uma vez para gerar o script, reutilize para sempre.

REGRA 02

Toda sessão termina com um artefato

A próxima sessão deve conseguir lê-lo em menos de 5k tokens. Se sua transição precisa do transcript completo, você não terminou a sessão.

REGRA 03

Subagents para busca, contexto principal para síntese

Não polua o thread principal com exploração. Envie o trabalho bagunçado para fora; mantenha seu contexto limpo para o raciocínio.

REGRA 04

Modo de planejamento é gratuito — use-o primeiro

Antes de qualquer sessão tocando >10 arquivos, planeje. Alinhamento antecipado não custa nada e economiza horas de trabalho na direção errada.
